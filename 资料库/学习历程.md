## 已验证的关键认识

- 对话模型每轮只看到程序发来的 messages；所谓“记忆”需要由程序保存并再次发送。
- 可以保留完整本地对话历史，同时只把最近若干轮发给模型，以控制上下文长度。
- 流式 API 返回多个片段；逐段展示的输出代码要在循环中执行，而首段提示只应触发一次。累计片段后再拼接并保存完整 assistant 回复，下一轮才能接着聊。
- 首段等待计时应在每次请求前重新开始；放到程序启动时计时会把用户输入和之前对话的耗时也算进去。
- `git add` 暂存改动，`git commit` 保存到本地仓库，`git push` 才上传远端；每一步都可以通过状态和差异检查确认。
- 用对照实验验证模型行为；只观察一种提示格式容易把偶然现象误当成规律。

## 踩过的坑

- 逐段打印语句若误缩进到仅执行一次的条件里，后续流式片段不会显示。
- 计时变量和“是否首段”的标记必须每轮请求重置，否则后续轮次提示不再出现，计时结果也失真。
- Git 工作区出现换行符提示不一定是提交失败；应检查状态、暂存差异和最终推送输出。
- 模型对自己身份的回答可能是生成内容，不能当作运行时模型配置的可靠证据。
